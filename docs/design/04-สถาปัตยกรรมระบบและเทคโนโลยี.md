# 4. สถาปัตยกรรมระบบและเทคโนโลยี

## 4.1 ภาพรวมสถาปัตยกรรม

ระบบแบ่งเป็น 2 ฝั่งผู้ใช้ที่ใช้งานผ่านช่องทางต่างกัน แต่เชื่อมกับ backend/ฐานข้อมูลชุดเดียวกัน:

```
┌─────────────────────┐        ┌──────────────────────┐
│  Web Back Office     │        │  ช่องทางสมาชิก         │
│  (เจ้าหน้าที่/ผู้บริหาร) │        │  (LINE LIFF mini-app) │
└──────────┬───────────┘        └───────────┬──────────┘
           │            REST/RPC API         │
           └───────────────┬──────────────────┘
                            │
                  ┌─────────▼─────────┐
                  │   Application      │
                  │   Server + Auth    │
                  └─────────┬─────────┘
                            │
                  ┌─────────▼─────────┐
                  │   PostgreSQL       │
                  └─────────┬─────────┘
                            │
              ┌─────────────┴─────────────┐
       ┌──────▼──────┐             ┌──────▼──────┐
       │ ไฟล์นำเข้า     │             │ LINE OA /   │
       │ (Payroll/    │             │ SMS Gateway │
       │  Bank file)  │             │             │
       └─────────────┘             └─────────────┘
```

## 4.2 ทางเลือกช่องทางฝั่งสมาชิก

| ทางเลือก | ต้นทุนพัฒนา | การเข้าถึงสมาชิก | ความสามารถแจ้งเตือน | ความต้องการ offline |
|---|---|---|---|---|
| **Web Portal** | ต่ำ-กลาง | ต้องจำ URL/รหัสผ่านแยก | ต้องพึ่ง SMS/อีเมลเพิ่ม | ต่ำ (ใช้ browser) |
| **LINE LIFF mini-app** | กลาง | สูงมาก — ครูไทยส่วนใหญ่ใช้ LINE อยู่แล้วในชีวิตประจำวัน | สูง — ผูกกับ LINE OA push ได้ทันที ไม่ต้องมี infra แยก | ต่ำ (ใช้ในแอป LINE) |
| **Native Mobile App** | สูง | สูง แต่มีแรงเสียดทานจากการติดตั้งผ่าน app store | สูง แต่ต้องทำ push notification infra เอง | สูงกว่า (รองรับ offline ได้ดีกว่า) |

**คำแนะนำ**: เริ่มด้วย **LINE LIFF mini-app** สำหรับสมาชิก เพราะ (1) ไม่มีแรงเสียดทานการติดตั้ง — เปิดจาก LINE OA ที่มีอยู่แล้วได้ทันที (2) ผูกกับโมดูลแจ้งเตือน (2.4) ได้โดยตรงผ่าน LINE Messaging API ไม่ต้องสร้างระบบ push แยก (3) ต้นทุนพัฒนาต่ำกว่า native app อย่างมีนัยสำคัญ เหมาะกับทีมเล็ก ส่วน native app ผลักไปเป็น Phase 3+ หากมีความต้องการเฉพาะที่ LIFF ทำไม่ได้ (เช่น biometric, offline เต็มรูปแบบ)

ฝั่งเจ้าหน้าที่ใช้ **เว็บ back office แบบดั้งเดิม** เพราะงานคีย์ข้อมูลปริมาณมากและดูรายงาน/ตารางข้อมูลซับซ้อนเหมาะกับจอคอมพิวเตอร์มากกว่าจอมือถือ

## 4.3 เทคสแต็กที่แนะนำ

ออกแบบสำหรับทีมพัฒนาขนาดเล็ก/นักพัฒนาคนเดียว เน้นเสถียรภาพและดูแลรักษาง่ายมากกว่าความทันสมัย:

- **Frontend (Back Office)**: framework แบบ full-stack เดียวที่ทำได้ทั้ง SSR และ API (เช่น Next.js หรือเทียบเท่า) — ลดจำนวน service ที่ต้อง deploy แยก
- **Frontend (สมาชิก)**: เว็บแอปภายใน LIFF (ใช้ framework เดียวกับ back office เพื่อลด context switching ของทีม)
- **Backend/API**: รวมอยู่ใน framework เดียวกัน หรือแยก service เฉพาะงานหนัก เช่น การประมวลผลไฟล์นำเข้า/กระทบยอด
- **ฐานข้อมูล**: PostgreSQL — รองรับธุรกรรมทางการเงินที่ต้องการ ACID, มี extension เพียงพอสำหรับ reporting queries
- **Authentication**: ฝั่งเจ้าหน้าที่ใช้ username/password + MFA; ฝั่งสมาชิกใช้ LINE Login (ผูกกับ LIFF) ร่วมกับการยืนยันเลขสมาชิก
- **Hosting**: เลือกแพลตฟอร์ม managed เดียวที่รองรับทั้ง web app และ PostgreSQL เพื่อลดภาระ DevOps ของทีมเล็ก
- **การนำเข้าไฟล์**: job/queue แยกต่างหากสำหรับประมวลผลไฟล์ CSV/Excel ขนาดใหญ่แบบ asynchronous ไม่บล็อก request หลัก

รายละเอียด version/library เฉพาะเจาะจงจะสรุปเมื่อเข้าสู่เฟสพัฒนาจริง เพื่อให้เลือกตามเวอร์ชันที่เสถียรที่สุด ณ ตอนนั้น
